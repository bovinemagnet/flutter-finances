= Receipt capture
Paul Snow
:revnumber: 0.0.0

A receipt enters the application through one of several routes. Whatever the route, the file is validated, written to the encrypted vault and committed before the application reports it saved, and reading the text is a separate step that can fail without losing the document. This page describes what the client does today; see xref:domain:receipts.adoc[] for the receipt model and xref:platform:capabilities.adoc[] for which capabilities each platform reports.

== Capture routes

[cols="2,3,2",options="header"]
|===
| Route | Behaviour | Platforms

| Scan receipt | `scanReceipt` opens the native document scanner, falling back to a basic camera capture | Mobile (scanner); desktop uses an image picker
| Import file | File picker for `jpg`, `jpeg`, `png`, `heic`, `heif` and `pdf` files, multiple selection allowed | All
| Paste | `Ctrl+V` or the *Paste* chip on the Receipts page; an image on the clipboard is saved as `pasted.png`, otherwise copied files are read | All (shown when the paste capability is true)
| Drag and drop | Dropping images or PDFs on the Receipts page; a "Drop to save as a receipt" overlay is shown | Desktop (the drag and drop capability)
| Share target | Files shared from another application into the app | Android and iOS (iOS needs the extension target; see the share extension section of xref:building-and-releasing.adoc[])
| Email forwarding | Documents attached to emails sent to a private forwarding address are collected after a sync and saved with the source `CaptureSource.email`; see <<Email forwarding>> | All (needs sync and an available service)
|===

Importing a file is always available and does not need camera or photo access, so a refused permission never blocks capture (UX 04).

== Scanner with camera fallback

`FallbackReceiptScanner` (`apps/finance_app/lib/platform/services.dart`) wraps a preferred scanner and a fallback. `main.dart` builds it from `NativeDocumentScanner` and `BasicCameraScanner`.

. If the native scanner is available, it is tried first. It captures up to 10 pages (`noOfPages: 10`) with edge detection and perspective correction supplied by the platform scanner.
. If it fails because the scanner module, its downloaded resources or Google Play services are missing, the failure is reported as `unavailable` and the basic camera capture runs instead. The fallback scanner needs no downloaded resources.
. A user cancelling, or a denied camera permission, is not retried. These are reported to the caller.
. `usedFallback` records whether the last capture had to use the fallback.

On desktop `BasicCameraScanner` is created with `fromLibrary: true`, so *Scan receipt* picks images from disk rather than opening a camera. If no scanner reports itself available, `scanReceipt` goes directly to the file picker.

When capture fails, the interface explains why instead of failing silently: a denied permission offers an *Import* action ("Camera access was not allowed. You can still import a photo or PDF."), and other failures show the reason from the platform.

=== Acceptance scenario A05

A05 is "Capture a receipt in flight mode on first launch". The expected result is that a readable image is saved, and that an absent scanner or missing OCR resources lead to a clear fallback. In the code this relies on three behaviours:

* the fallback scanner above, which needs no downloaded resources;
* saving the image before any text reading, so the document is kept whatever happens next; and
* a message after saving: "Receipt saved on this device", followed by either "Receipt read; ready to review" or "The receipt could not be read; enter the details when reviewing".

Saving a receipt never posts an expense. See xref:sync:offline.adoc[].

== Validation and storage

`ReceiptService.capture` (`apps/finance_app/lib/data/receipt_service.dart`) validates every file with the shared content checks in `finance_core`, using the default `ContentLimits`:

[cols="2,1",options="header"]
|===
| Limit | Default

| File size | 20 MiB
| Pages per receipt | 10
| Longest image edge | 16,384 pixels
| Decoded image area | 50,000,000 pixels
|===

The server applies the same limits when an upload completes (see xref:domain:receipts.adoc[]).

If any file is rejected, or the page total is over the limit, nothing is saved and the messages are shown. Otherwise each file is saved as a source asset in the vault, one receipt page record is created per page, and then the receipt record is written. Only after that does the application report the receipt as saved (REC 03).

== Metadata stripping

New copies made by the application lose metadata that can reveal location (REC 02). Files whose source is `camera`, `documentScanner` or `paste` pass through `stripImageMetadata` (`apps/finance_app/lib/platform/image_metadata.dart`). Files that were imported, dropped or shared are preserved exactly as received.

* *JPEG:* the EXIF and XMP segment (APP1), the IPTC segments (APP12 and APP13), the other APP3 to APP11 and APP15 segments, and comments are dropped. JFIF (APP0), the ICC profile (APP2) and the Adobe colour transform (APP14) are kept so the image renders identically.
* *PNG:* the `eXIf`, `tEXt`, `zTXt` and `iTXt` chunks are dropped.
* Other content is returned unchanged. A malformed JPEG or PNG is also returned unchanged rather than partly stripped.

== Reading the text

After saving, `saveCapturedReceipt` asks the configured `TextRecogniser` whether it is available and, if so, runs `ReceiptService.extract`. The engine is chosen in `main.dart` from the capabilities.

[cols="1,2,2",options="header"]
|===
| Engine | Used when | Notes

| `MlKitTextRecogniser` | Android and iOS | ML Kit Text Recognition v2, Latin script; reported as engine `mlkit-text-v2`
| `PdfiumPdfReader` | PDFs, on all platforms | Implements `PdfReader` using PDFium. Reads the PDF's own text; reported as engine `pdf-text`
| `TesseractTextRecogniser` | Always on desktop | Checks for itself whether `tesseract` is installed with English data; runs the `tesseract` command line with `-l eng --psm 4`; reported as engine `tesseract` with its version string
| `UnavailableTextRecogniser` | Mobile, when on-device OCR is not available | Receipts are kept and the fields are entered by hand
|===

On desktop, `PlatformCapabilities.detect` runs `tesseract --list-langs` at start-up. The on-device OCR capability is true only if the output includes `eng`. If Tesseract is not installed, or has no English data, the receipt is saved without reading and the person enters the details. The app says so rather than failing silently: at capture it shows "Receipt saved on this device" followed by the recogniser's `unavailableMessage`, the review screen shows a card with the message and "Enter the details by hand.", and Settings, under "Reading receipt text", shows the message too. On desktop the message names what to install: "Reading text needs Tesseract with English language data installed".

Both engines produce an `OcrResult`, which the shared parser in `finance_core` turns into suggested fields. Extraction behaves as follows:

* PDF receipts are read on the device. `ReceiptService.extract` reads a PDF's own text page by page, up to 10 pages. A page with fewer than 20 non-space characters counts as having no text of its own, so it is drawn as an image (200 dots per inch, longest edge at most 2,500 pixels) and sent through the text recogniser above. A PDF with text therefore needs no recognition engine, while a scanned PDF needs one. The engine is recorded as `pdf-text`, or `pdf-text+<engine>` when a receipt mixes the two. A PDF that is damaged or password protected, or a scan on a device with no engine, moves to "Could not be read" and is kept for entering by hand. Reading only fills proposals for review.
* Any exception during extraction moves the receipt to the "Could not be read" state. The document is kept, and retry and manual entry remain available (REC 04).
* A review or a deletion made while a receipt is being read stands. The result of that reading is dropped when it finishes, rather than overwriting the person's decision or bringing a deleted receipt back.
* If the application stops before or during reading, the Receipts page shows "Not finished being read" for a receipt caught part-way through, and the review screen offers *Try again* on the device that holds the original.
* A receipt that needs review can be read again, for example from cloud text, which replaces the suggestions and leaves confirmed values alone. A reviewed receipt is not read again, because that could offer a second expense for the same purchase.
* Extraction never creates an expense by itself. The person reviews the suggested fields and chooses to create an expense or attach the receipt to an existing transaction (REC 06, OCR 04, A07).

The Receipts page lists receipts with their state ("Saved, waiting to be read", "Reading", "Needs review", "Reviewed" or "Could not be read"), whether they are matched, and, for a workspace that syncs, whether they are saved on this device only. It can be filtered to unmatched receipts and to receipts that could not be read.

If the device runs out of storage while a receipt is written, nothing is left half saved and the application says "Not saved: this device is out of storage. Free some space and try again." Any other write failure shows "Not saved: the receipt could not be written to storage."

== Email forwarding

A member can forward receipts by email to a private address. Forwarding only ever creates a receipt for review; it never posts a transaction.

=== Turning it on

In Settings, under Sync, the "Forward receipts by email" screen lets a member turn on a private forwarding address. The screen appears only when sync is on and the sync service reports that forwarding is available. The member can copy the address, replace it or turn it off. Each member has their own address, and mail sent to a replaced or revoked address is dropped. The screen also lists up to 20 recent emails and what became of each, newest first.

=== What happens to an email

An email passes through an outside inbound email service and then the sync service. The body is discarded and never stored. The sender and subject are kept with the message record.

The server identifies each attachment from its bytes (JPEG, PNG, HEIC or PDF) rather than from its name or declared type, and scans it. Only a byte order mark and whitespace may come before a PDF header, so a file that carries a PDF header further in, such as an executable, is refused. The following limits apply:

[cols="2,1",options="header"]
|===
| Limit | Value

| Size of one attachment | 20 MB
| Attachments per message | 10
| Messages per address per day | 50
|===

Inline images under 20 KB are ignored, as they are usually logos or signatures.

=== Collection on the device

After each successful sync, the device collects the documents that are waiting. Each one goes through the ordinary capture path with the source `CaptureSource.email`, so it is validated and saved in the vault like any other receipt. The device acknowledges a document only once the receipt is durably saved locally, and the server then deletes its copy. Collecting the same document again does not create a second receipt. Once collected, the receipt is shared with the workspace like any other receipt.

Images go through text recognition as described in <<Reading the text>>. Recognition runs alongside collection and does not hold it up. Forwarded PDFs are read as described in <<Reading the text>>, and appear under "Could not be read" only if that fails, in which case the details can be entered by hand, just as for a PDF imported directly.

A download has up to five minutes, because an attachment can be 20 MB on a slow connection.

If saving a document keeps failing on a device, or its download keeps arriving damaged, that device stops trying after three attempts until the application next starts. The document stays waiting and is not rejected. A dropped connection does not count as an attempt.

A device that already holds the receipt for a waiting document acknowledges it without downloading it again. If the application stopped after saving a document and before acknowledging it, the next collection also reads it, on the device that holds the original. A device that only knows of the receipt from another device leaves the reading to that device.

If two devices both save and read the same document, for example because one lost its connection before acknowledging it, the first reading to reach the sync service is kept. The other device quietly drops its own reading and takes that one, so nobody is asked to choose between two results they never entered. A failed or unfinished read is not a reading, so a real one replaces it. Anything a person changed on the receipt on that device, such as confirmed details or a deletion, is not dropped and goes to the usual conflict review.

=== Problems that are reported

The Receipts page reports, rather than captures:

* an email with no attachment;
* an attachment the server refused;
* the daily limit being reached; and
* a processing failure.

Up to three emails show on the Receipts page at a time. Each names up to three refused files and counts the rest, and a count of further emails follows. Each can be dismissed.

A document that the device refuses, for example an encrypted PDF or one over 10 pages, is reported back to the server and is not retried.

=== Retention

Documents that are not collected, and message records, are deleted after 30 days. If a document has failed to reach a device for a week, that device says so on the Receipts page, while there is still time to forward the email again.

=== Availability

Only a `sandbox` provider exists today (`finance.inbound-mail.sandbox.enabled`); choosing a real inbound email service is a pending decision. Without a provider, a token key and a domain, the service reports forwarding as unavailable and the app hides the screen.

== Making a photo readable

The receipt review screen offers "Improve readability" for a page of a receipt that is an image (not a PDF); for a receipt of several pages the user chooses which page to edit, opening "Make it readable" (`features/receipts/image_edit_screen.dart`), for photos that no native scanner has corrected (REC 02). The user can rotate in quarter turns, crop the sides and the top and bottom, and "Enhance faded text", which stretches contrast between the 2nd and 98th percentile of brightness on a greyscale copy (`lib/platform/image_tools.dart`). "Save copy" stores the result as a JPEG readable derivative without metadata, attached to that page. The original file is kept exactly as captured. The page preview shows the derivative when there is one, text recognition reads each page through `readPage`, which prefers the readable derivative when one exists, and saving a new copy replaces the previous derivative.

== Warnings

When a receipt is reviewed, the application checks it and shows warnings. A warning never blocks saving or posting.

* "The photo looks blurred; check the details are readable": the variance of the Laplacian on a downscaled greyscale copy is under 100.
* "The photo is small; the text may be hard to read": both sides are under 600 pixels.
* "This exact file is already saved as another receipt": another receipt has an asset with the same SHA-256.
* "This looks like a photo of a receipt already saved": the difference hash of the image is close to that of another receipt's image (MATCH 02).

The duplicate warnings name the other receipt so the user can open it. PDFs are not assessed for blur or size. A damaged image cannot be assessed for blur or size either, but still gets the duplicate warnings, and the review screen says it cannot be shown rather than leaving the preview blank.

== Separating pages

A document of several receipts, such as a multi-page PDF or a scan with several pages, is saved as one receipt. On the review screen, "Separate pages" lets the user pick a page that becomes its own receipt (REC 05). The new receipt shares the same source file and keeps any readable derivative; the remaining pages are renumbered. Splitting is manual: the application does not detect where one receipt ends.

== Date convention

A receipt date such as 03/04 is ambiguous. In settings, "Receipt dates like 03/04" chooses whether it is read day first ("3 April", the default) or month first ("4 March"). The choice is passed to the parser as the `DateConvention` and applies to receipts read afterwards (OCR 04). The other reading is still kept as an alternative for the user to choose.

== PDF preview

For a PDF receipt, the review screen draws the actual page. The page is rendered once, however often the screen rebuilds. If the page cannot be drawn, or no PDF engine is available on the device, the screen shows an icon instead.

== Exporting receipts

Settings has "Export receipts" (EXP 01). It writes every receipt's original source files, unchanged, to a folder, named `<receiptId>-<n>` with an extension from the content type, and a `manifest.json` (`format` `finance.receipts`, `formatVersion` 1). For each receipt the manifest holds the capture time, the confirmed or suggested merchant, date, total and tax, the currency, the linked journal ids, and for each file its name, SHA-256 and content type. A file whose bytes are held only on the server is listed with no file name and the note "stored only on the server". Readable derivatives are not exported. How the folder is delivered depends on the device; see xref:domain:exports-and-backups.adoc#delivering-files[Delivering files].
