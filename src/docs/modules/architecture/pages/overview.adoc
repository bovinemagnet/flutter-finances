== Components and responsibilities

The client reads from its local database and writes local commands into a durable outbox. The sync service validates commands, commits canonical changes and exposes a cursor-based change feed. Receipt bytes travel directly to private object storage through short-lived presigned URLs; they do not travel through the financial command payload.

== Modular monolith

The backend is a modular monolith with explicit module boundaries, not a microservice estate. The API and worker are deployed from the same codebase and image with independently controlled workloads (`finance.worker.enabled`). A PostgreSQL job table, claimed with `FOR UPDATE SKIP LOCKED`, is the only queue; a dedicated queue is introduced only when measured workload justifies it.

The server modules are `common`, `workspace`, `sync`, `ledger`, `receipts`, `imports`, `exports`, `jobs`, `deletion` and `storage`. They are declared as Spring Modulith application modules, and `server/finance-core` is a separate Gradle subproject. See xref:architecture:sync-service.adoc[] and xref:architecture:repository-layout.adoc[].

== Data flow

.Local save and synchronisation
[source,mermaid]
----
include::example$local-save-sync-sequence.mmd[]
----

. A user action is validated locally and saved with its outbox command in one SQLite transaction (`BEGIN IMMEDIATE`, write-ahead log, `synchronous = FULL`). The local projection updates immediately and the entry shows an unsynced indicator.
. When the workspace is in synced mode, the sync client takes pending outbox commands in order, in batches of up to 500, and posts them to `POST /v1/sync/commands`. Each command keeps its `commandId` for life, so a retry is idempotent.
. The server validates each command and commits canonical state, its idempotency record and a change record in one transaction. Each command receives a result status: `applied`, `previously_applied`, `conflict`, `validation_failed` or `permission_denied`.
. The client records the results on the outbox entries (conflicts and rejections become review items), then pulls `GET /v1/sync/changes` with an opaque cursor and applies each page and the new cursor in one transaction. If the cursor is older than the tombstone horizon, the client rebuilds from `GET /v1/sync/snapshot`.
. Receipt files are saved to the encrypted vault first. The sync client then requests an upload intent (`POST /v1/receipts/upload-intents`), `PUT`s the file bytes to the presigned URL, and completes the upload (`+POST /v1/receipts/{receiptId}/complete+`). The server checks size, checksum and content type before the document is released.

The protocol is described in xref:sync:protocol.adoc[].

[NOTE]
====
`SyncClient` is implemented and tested in `finance_store`, but the application in `apps/finance_app/lib` does not yet construct one: the screens read and write through `AppState` and `FinanceStore`, and the background-sync adapter is a placeholder. Local-only operation is therefore the complete path in the application today. The OIDC code (`lib/data/oidc.dart`) is likewise present but not yet connected to a sign-in screen.
====

== API style

The offline command protocol, imports, receipts, exports and workspace deletion use REST under `/v1`, with OpenAPI generated by springdoc (`/v3/api-docs`), versioned command envelopes and explicit idempotency keys. GraphQL may later serve complex read views but must not become a second set of mutation semantics.

== Client structure

Business rules live in a pure Dart package (`finance_core`) with no Flutter and no IO. Persistence (`finance_store`), platform services and UI are separate. Platform interfaces keep operating system conditionals out of finance code; see xref:platform:capabilities.adoc[] and xref:architecture:client-application.adoc[].
