= Receipts
Paul Snow
:revnumber: 0.0.0

A receipt is a captured document plus the values the user confirmed from it. A receipt is _evidence_, not money: attaching or creating from a receipt never posts a second expense on its own. The code lives in `packages/finance_core/lib/src/documents/` (`receipts`, `validation`, `extraction`), with server-side checks in `server/app/src/main/java/com/paulsnow/finance/server/receipts`. Capturing the image on a device is covered in xref:platform:receipt-capture.adoc[].

== Model

* `Receipt` holds the capture time (UTC), the `CaptureSource` (`camera`, `documentScanner`, `photoLibrary`, `shareTarget`, `fileImport`, `paste`, `dragAndDrop`), the extraction state, the _confirmed_ fields, the latest extraction id, the review outcome, notes, tags and an optional `deletedAt` tombstone.
* `ReceiptFields` are merchant, date, total, tax and a refund flag. The total is a positive magnitude in the receipt's currency.
* `ReceiptPage` numbers the pages of a receipt from 1. A multi-page PDF has one page per source page index, all sharing one source asset.
* `DocumentAsset` is one stored file, either the `source` as captured or imported, or a `readableDerivative` (cropped, deskewed or enhanced). It records the lower-case SHA-256, size, page count and upload state.

Extraction candidates are never written to the receipt. They live on a separate, immutable `Extraction` record, so running extraction again can add suggestions but can never overwrite something the user confirmed.

== States and the state machine

Two state machines run independently (`receipt_states.dart`). A receipt can be reviewed while its image is still uploading, and an extraction failure never affects the stored document.

[cols="1,3"]

|Event |Meaning

|`queue` |Hand a captured receipt to the extraction queue.
|`start` |A worker picks the receipt up.

|`fail` |Extraction failed; the document is kept.
|`retry` |Try a failed extraction again.
|`interrupt` |The worker stopped (for example the app was closed); the receipt is queued again.
|`review` |The user confirmed the fields, by review or manual entry. Allowed from `captured`, `extractionQueued`, `needsReview` and `extractionFailed`, so a receipt can always be completed by hand.
|`rerun` |Run extraction again, for example with a newer engine. Allowed from `needsReview` and `reviewed`; confirmed fields are kept.
|===

=== Upload

Each `DocumentAsset` has its own upload state (`UploadState`): `localOnly`, `uploadQueued`, `uploading`, `uploaded`, `uploadFailed`. Events are `queue`, `start`, `complete`, `fail`, `retry` and `interrupt` (a stopped transfer is queued again). `uploaded` has no outgoing transitions. `localOnly` is the state while sync is off.

A receipt shows the most urgent state of its assets, in the order failed, uploading, queued, local only, uploaded. A receipt with no assets (for example metadata that synced before its image) has no upload state.

An asset's local bytes may be evicted from the cache only when the asset is present, `uploaded` and its cloud copy is confirmed (`evictionStatus`). An unsynced original is never evicted.

== Validation limits

`validateDocument` checks a document from its bytes alone; the file extension never decides the type. Checks run in this order: empty, size, type, then type-specific structure, encryption, page count and image dimensions.

[cols="2,3"]
|===
|Limit (`ContentLimits` default) |Value

|Maximum file size |20 MiB (`20 * 1024 * 1024` bytes)
|Maximum pages per receipt |10
|Longest image edge |16384 pixels
|Largest decoded area |50,000,000 pixels (about 200 MB decoded at four bytes per pixel, which stops decompression bombs)
|===

Supported formats are JPEG, PNG, HEIC, HEIF and PDF, identified from magic bytes:

* JPEG: `FF D8 FF` at offset 0.
* PNG: the 8-byte PNG signature at offset 0.
* HEIC and HEIF: `ftyp` at offset 4. The HEVC brands `heic`, `heix`, `hevc`, `hevx`, `heim`, `heis`, `hevm` and `hevs` give HEIC; `mif1` and `msf1` give HEIF; any other brand is unsupported.
* PDF: `%PDF-` within the first 1024 bytes.

PDF inspection reads raw syntax only and never decompresses streams. It reports whether the file is readable (an `%%EOF` marker near the end, a `startxref`, and at least one page or a hidden page tree), whether an `/Encrypt` dictionary is named in a trailer or cross-reference stream, and a conservative page count (the larger of the visible `/Page` objects and the largest `/Count`). When the page tree is inside compressed object streams the count is unknown and a warning asks the platform renderer to confirm it. Image dimensions are read from the header (JPEG SOF, PNG IHDR, HEIF `ispe`, taking the largest) without decoding pixels.

Issues carry a stable code, an actionable message and a severity. `isAccepted` is true when there are no errors.

[cols="2,1,3"]
|===
|Code |Severity |Cause

|`EMPTY_FILE` |error |No bytes.
|`FILE_TOO_LARGE` |error |Over the size limit.
|`UNSUPPORTED_TYPE` |error |Not JPEG, PNG, HEIC, HEIF or PDF.
|`ENCRYPTED_PDF` |error |PDF is password protected or encrypted.
|`UNREADABLE_PDF` |error |PDF is truncated or has no recognisable structure.
|`TOO_MANY_PAGES` |error |More than 10 pages. `checkReceiptPageLimit` applies the same rule when pages are added to an existing receipt.
|`UNREADABLE_IMAGE` |error |JPEG or PNG header not found.
|`IMAGE_TOO_LARGE` |error |An edge or the area is beyond the limits.
|`DIMENSIONS_UNVERIFIED` |warning |HEIC or HEIF size cannot be read from the header; the device confirms it on decode.
|`PAGE_COUNT_UNVERIFIED` |warning |PDF page count is hidden in object streams.
|===

=== Server checks

The server repeats the checks when an upload completes, then scans it. Uploads go to a per-asset staging key. Completion verifies the checksum and the content type against the magic bytes (`CHECKSUM_MISMATCH`, `CONTENT_TYPE_MISMATCH`) and moves the asset to `quarantined`. A scan job then releases it (`available`) or marks it `rejected`. The default `StructuralDocumentScanner` rejects `TRUNCATED` and `MALFORMED` files, images beyond the configured dimension, and PDFs containing `/JavaScript`, `/JS`, `/Launch`, `/EmbeddedFile(s)`, `/XFA` or `/RichMedia` (`ACTIVE_CONTENT`). It is not a malware scanner; a deployment can supply its own `DocumentScanner` bean.

The server limits are configured under `finance.receipts` and match the client's `ContentLimits`: `max-size-bytes` (default 20,971,520, which is 20 MiB), `max-pages-per-receipt` (10), `max-image-side` (16,384 pixels) and `max-image-pixels` (50,000,000). At completion the server counts the pages of a PDF as the shared `pdf.inspect` fixture operation does (an image is one page) and refuses a receipt whose source documents total more than 10 pages with `TOO_MANY_PAGES`. The scan job rejects images beyond the side and area limits.

== Extraction, provenance and uncertainty

Text recognition sits behind a single boundary, `ExtractionProvider`, which returns an `OcrResult` (recognised text and geometry) and nothing more. Its `ProviderDataUse` states whether consent is required, the retention and the processing region. That text is untrusted: the deterministic `parseReceipt` function turns it into candidates, arithmetic and ledger validation stay local, and only the user can confirm fields, approve a match or post an entry.

Each `Extraction` records the original engine output (including engine name and version), the parser version (`receipt-parser/1`), and ordered candidates (best first) for merchant, date, total, tax and currency, plus optional subtotal, cash tendered and change. Every `FieldCandidate` carries its provenance: the indexes of the OCR lines that produced it and their joined text.

=== Confidence

Confidence is a category, never a percentage.

* `high`: corroborated by independent evidence (arithmetic, a payment line, a label) with nothing competing.
* `medium`: found by a keyword or position but not corroborated.
* `low`: inferred without a keyword, or competing values exist.

=== Parser heuristics

* Rows are rebuilt from geometry when every line has a box; a label row followed by an amount-only row is merged.
* Amounts need exactly two decimal places; percentages, quantities and dates are ignored; the last amount on a row counts.
* Totals come from rows labelled total. Cash tendered, change and cash-out rows are never totals. A candidate scores 8 when subtotal, discounts, charges, rounding (and tax, if exclusive) add up to it, 6 when a card payment row shows it, 6 when cash less change equals it, 2 for a strong label such as `total due`, 1 when printed more than once and 1 when it is the last total row. The best score wins and ties go to the earlier row.
* With no total row, the total is inferred from a payment row, then cash less change, then the subtotal, then the largest amount, and is marked `TOTAL_INFERRED`.
* Dates prefer labelled rows and skip due, expiry and validity dates. An all-numeric date with both parts at most 12 is ambiguous unless the merchant has a chosen convention; the workspace default is day-month, which the user can change to month-day in settings (see xref:platform:receipt-capture.adoc[]). The other reading is kept as an alternative, and a reading in the future gives way to one that is not.
* The merchant is a labelled value (`Sold by:`, `Merchant:`) with high confidence, otherwise the first heading-like row with medium confidence.
* Currency is reported only when printed as a code or prefixed symbol such as `AUD`, `A$` or `US$`; a bare `$` is not explicit.

=== Uncertainty reasons

`UncertaintyReason` codes mark a value, or the whole extraction (`reviewReasons`), as needing a careful look before anything is posted.

[cols="2,3"]
|===
|Code |Meaning

|`AMBIGUOUS_DATE` |Day-month and month-day readings are both plausible.
|`FUTURE_DATE` |The date is after today in the workspace timezone.
|`CONFLICTING_DATES` |Several different dates compete.
|`MULTIPLE_PLAUSIBLE_TOTALS` |Competing total candidates.
|`TOTAL_INFERRED` |No total row; the total was derived.
|`ARITHMETIC_MISMATCH` |Printed subtotal, charges and tax do not add up to the total.
|`CURRENCY_NOT_EXPLICIT` |No currency code printed; the workspace currency is assumed.
|`FOREIGN_CURRENCY` |An explicit currency differs from the workspace currency.
|`CONFLICTING_CURRENCIES` |More than one currency is printed.
|`REFUND_RECEIPT` |The receipt appears to be a refund.
|`MERCHANT_GUESSED` |Merchant taken from a heading rather than a label.
|`TAX_IMPLAUSIBLE` |Printed tax is not plausible for the total.
|`MISSING_MERCHANT`, `MISSING_DATE`, `MISSING_TOTAL` |Nothing was found for the field.
|===

=== What the review screen shows

`buildReceiptReview` merges the confirmed values with the latest extraction. Confirmed values always win and are never highlighted. An extracted value is highlighted when it is not high confidence or has a reason; a missing value is always highlighted. Other candidates are offered as alternatives.

== Line items

`extractReceiptItems` (`receipt_items.dart`, OCR 01, P1) reads the purchased lines of a receipt from the same OCR result as the header fields. Each `ExtractedLineItem` is a candidate only: it records the description, quantity (in thousandths, so 710 is 0.71 kg), unit, unit price, line total, any discount, whether GST applies, the OCR lines it came from and a confidence. It becomes a `ReceiptItem` (which also holds an optional category chosen by the user) only when the user confirms it. Items describe the receipt and never post a second expense.

Like an `Extraction`, an `ItemExtraction` is immutable evidence stamped with the parser version (`receipt-items/1`), so a rerun creates a new one. `reviewReceiptItems` keeps confirmed items as they are and offers the latest extraction's items as suggestions; a rerun can never replace or edit a confirmed item (OCR 03).

[cols="2,3"]
|===
|Heuristic |Behaviour

|Item rows |The rows before the first subtotal, total, tax, payment, cash or change row that has an amount. The last amount on a row is the line total.
|Quantity rows |`0.71 kg @ $4.00/kg` or `2 @ 1.50` gives the item above it its quantity, unit and unit price. With a trailing amount it completes a description-only row above. A trailing `x2` is read too.
|Discounts |A row with a negative amount reduces the item above it. Positive "saved" rows are informational and ignored.
|GST |A row starting `*`, `#` or `^`, or an amount followed by the tax code `A`, `G` or `T`, marks GST. When some item is marked, unmarked items have GST false; when none is, it is unknown.
|Line arithmetic |Quantity times unit price, rounded half away from zero, must equal the line total, otherwise `ITEM_ARITHMETIC_MISMATCH`.
|===

Reconciliation compares the items with the printed amounts: `consistent` when the items' net total equals the subtotal, or the total after the discounts, charges and rounding printed between them (with or without the printed tax); `inconsistent` (`ITEMS_DO_NOT_RECONCILE`) when a subtotal or total exists and neither holds; `insufficient` without items (`NO_ITEMS_FOUND`) or without a subtotal and total (`ITEMS_NOT_CHECKED`). Item confidence is high when consistent, medium when insufficient, and low when inconsistent or the line's own arithmetic fails.

In the application, `ReceiptService` extracts items every time it extracts the header fields, saves the latest `ItemExtraction` per receipt, and the review screen lists them under "Items" with the reconciliation result ("The items add up to the total", "The items do not add up to the total; check them" or "Not enough was read to check the items").

== Warranties

A `Warranty` (`warranty.dart`, P1) belongs to a receipt, optionally to one confirmed item. It has a description, a start date (the purchase date by default), a period of calendar months (clamped to shorter months) plus days, and a list of reminder lead times in days (default 30). A warranty needs a positive period. `expiresOn` is the start plus the period, less one day, and `isActiveOn` tests a date against the cover.

`warrantyReminders` plans a `PlannedReminder` for each lead time, before the expiry date, in date order. They share the quiet-hours rule and the privacy default of schedule reminders (see xref:domain:planning.adoc#_reminders[Reminders], PLAN 04): the text is "A warranty ends on <date>" unless the preference shows details, in which case it names what is covered. Reminders already in the past are left out, and none are planned when reminders are disabled.

In the application, "Add warranty" on the review screen asks what is covered and the number of months, starts the cover on the receipt's confirmed date (or today), and can remove it again. `planReminders` in `apps/finance_app/lib/data/reminders.dart` adds the warranty reminders to the schedule reminders as local notifications titled "Warranty ending", for the next 30 days, with the private wording unless the details are opted in.

== Separating multi-receipt documents (REC 05)

A scan or PDF may hold several receipts. REC 05 has the user split a multi-receipt PDF manually in P0 and makes automatic separation a P1 feature. `proposeReceiptSeparation` (`receipt_separation.dart`, P1) takes one `OcrResult` per page and proposes where each receipt starts. It is a proposal only: nothing is split, created or changed until the user confirms.

Every page after the first is scored, and a score of 2 or more starts a new receipt.

[cols="3,1"]
|===
|Evidence |Score

|Previous page printed a total and this page opens with a merchant heading (`MERCHANT_HEADER_AFTER_TOTAL`) |+3
|Previous page printed a total but this page has no heading (`PREVIOUS_PAGE_TOTALLED`) |+1
|This page and the previous one each print a total (`PAGE_HAS_OWN_TOTAL`) |+1
|The heading names a different merchant (`DIFFERENT_MERCHANT`) |+2
|A different date (`DIFFERENT_DATE`) |+1
|A `Page 1 of n` marker (`FIRST_PAGE_MARKER`) |+2
|Previous page has no total (`PREVIOUS_PAGE_WITHOUT_TOTAL`) |-2
|No merchant heading (`NO_HEADER`) |-1
|A `Page k of n` (k above 1) or `continued` marker (`CONTINUATION_MARKER`) |-3
|===

A start scoring 4 or more is high confidence, 3 medium and 2 low. A continuation scoring -2 or less is high, -1 or 0 medium and 1 low. A page with no recognised text (`BLANK_PAGE`) joins the current receipt with medium confidence. The first page is always a start (`DOCUMENT_START`).

Consecutive pages form a `ReceiptPageGroup` with the weakest decision's confidence (at most medium when no page prints a total, `NO_TOTAL_FOUND`) and a merchant and date hint. A page that holds a total, a new merchant heading, items and another total is flagged `MULTIPLE_RECEIPTS_ON_PAGE`: separation stops at page level, so the group is marked `needsManualSplit`, its confidence is low and the user splits that page by hand. `isSingleReceipt` is true when the whole document looks like one receipt.

In the application, "Suggest how to split" appears on a receipt with more than one page. It recognises each image page on the device (PDF pages are not read, and the button explains when text recognition is unavailable), then either says it looks like a single receipt or asks "Split into n receipts?" with each group's pages and a warning where a page holds more than one receipt. Only on confirmation does `applySeparation` split the pages into new receipts.

== Optional cloud text

When the workspace is synced, the review screen offers "Use cloud text". It fetches text that the server read after cloud recognition was allowed and passes it to `ReceiptService.extractFromText`, which wraps it as an `OcrResult` from the engine `cloud` and runs the same parser as for on-device text. If the server has no text for the receipt, the screen says so. The cloud adapter is optional and consented separately (AUTO 02); see xref:sync:cloud-extraction.adoc[] for the service side.

The text is untrusted. It only produces candidates and item suggestions on an `Extraction` and an `ItemExtraction`; it cannot confirm a field, approve a match, post an entry or invoke any command. The user still reviews everything exactly as for on-device text.

== Review outcomes

`reviewReceipt` completes review with the user's confirmed fields and one `ReviewDecision`. It first applies the `review` event (so it fails with `IllegalTransitionException` while the receipt is extracting), merges the fields, then records a `ReviewOutcome`.

[cols="1,3"]
|===
|Decision and outcome |Behaviour

|`AttachToTransaction` -> `attachedToTransaction`
|Links the receipt to an existing entry; nothing is posted (acceptance scenario A07). The allocation defaults to the receipt total only when it equals the entry amount; otherwise the user must confirm a partial allocation (`ALLOCATION_REQUIRED`).

|`CreateExpense` -> `expenseCreated`
|Builds a `TransactionDraft` (a refund type for refund receipts) from the confirmed fields, validates it by building the journal once and discarding it, and returns the draft and a link to it. Posting is a separate, explicit step through the normal command path.

|`KeepDocumentOnly` -> `documentOnly`
|Keeps the document with no financial entry.
|===

Review errors (`ReviewErrorCode`): `MISSING_TOTAL`, `MISSING_DATE`, `CURRENCY_MISMATCH`, `UNKNOWN_ACCOUNT`, `CASH_ACCOUNT_REQUIRED` (a cash purchase must use a cash account), `CASH_ACCOUNT_UNCONFIRMED` (a cash account must be explicitly confirmed), `ALLOCATION_REQUIRED`, `INVALID_LINK` and `INVALID_DRAFT`.

A `ReceiptTransactionLink` records the user-confirmed relationship and the allocated amount. `LinkError` codes are `NON_POSITIVE_ALLOCATION`, `CURRENCY_MISMATCH`, `AMOUNT_MISMATCH`, `DUPLICATE_LINK`, `JOURNAL_NOT_LINKABLE`, `EXCEEDS_TRANSACTION_AMOUNT` and `EXCEEDS_RECEIPT_TOTAL`. Finding the entry for a receipt is described in xref:matching-and-deduplication.adoc[].

== Retention and deletion

Documents are kept until the user deletes them deliberately. `planDocumentDeletion` produces a plan and does not touch the ledger.

* The receipt is marked deleted with `deletedAt` (UTC) and kept as a tombstone for sync.
* The plan lists the assets, pages and links to remove.
* `journalIdsKept` lists the journals that lose their link, so the interface can say that the financial transaction is unchanged. Journals are never part of the plan.

Cache eviction of local bytes is separate from deletion and is described under Upload above. The server removes a deleted workspace's receipt records through `ReceiptsPurger`; see xref:operations:data-deletion.adoc[]. There is no time-based automatic retention policy in the code.
