= Exports and backups
Paul Snow
:revnumber: 0.0.0

Two things leave the app: CSV exports for use in spreadsheets, and the portable archive that is a real backup. CSV alone is not a backup. The core code is in `packages/finance_core/lib/src/documents/exports`; the encrypted archive writer and reader are in `packages/finance_store/lib/src/backup`. For the operational procedure see xref:operations:backup-and-restore.adoc[].

== CSV export

`encodeCsv` writes RFC 4180 CSV with CRLF line endings, each row ending in CRLF. A field is quoted when it contains the delimiter, a quote or a line break, and embedded quotes are doubled.

=== Formula sanitisation

Spreadsheet applications treat a cell that starts with certain characters as a formula. `sanitiseCsvValue` prefixes an apostrophe when a text value starts with `=`, `+`, `-`, `@`, a tab or a carriage return. It is applied to every text field (account, payee, category, type, status, notes, tags, owed by, journal id and report headers) and not to amounts, which are written as plain decimals so they stay numbers.

=== Transaction export

`exportTransactionsCsv` uses the columns `Date`, `Account`, `Payee`, `Category`, `Amount`, `Currency`, `Type`, `Status`, `Notes`, `Tags`, `Owed by`, `Journal ID`.

* One row per category line, so split entries sum correctly. Entries without categories, such as transfers, give one row per account line, the entry's own account first.
* Amounts are signed from the account's point of view (negative is money out).
* Rows are ordered by effective date, entered time and id.
* `TransactionExportFilter` selects a date range, accounts, whether to include pending entries and whether to include corrections. By default only posted entries are exported; corrected originals and their reversals cancel out and are left out unless corrections are requested.

In Settings, "Export transactions (CSV)" opens a dialog to choose a period (all time by default, or the same periods as Reports), an account (all by default) and whether to include pending entries (off by default). The defaults export the same entries as before. A chosen period appears in the file name, for example `transactions-2026-10-01-to-2026-10-31.csv`; otherwise the name uses today's date.

`exportReportCsv` exports report rows. Money becomes a plain decimal, numbers, dates and booleans are written as they are, null is empty, and anything else is sanitised.

== Archive manifest

`ArchiveManifest` describes a portable archive (version constants `archiveFormatVersion` 1 and `archiveSchemaVersion` 1, the latter matching the sync schema version).

[cols="2,3"]
|===
|Field |Content

|`formatVersion`, `schemaVersion` |Layout and entity JSON versions.
|`createdAt` |UTC instant.
|`workspaceId`, `currency`, `timezone` |Workspace identity, currency with exponent, and IANA timezone such as `Australia/Sydney`.
|`effectiveDateSemantics` |States that effective dates are calendar dates (`YYYY-MM-DD`) in the workspace timezone, and technical timestamps are UTC ISO 8601.
|`acceptedRevision`, `acceptedCursor` |Last server revision and change feed cursor, for synced workspaces.
|`pendingLocalChanges` |Commands not yet accepted by the server, recorded apart from the accepted state.
|`files` |Each file's path, SHA-256, size, role (`data`, `receiptSource`, `receiptDerivative`, `csvView`), content type and asset id.
|`entityCounts` |Record count per entity type, written in sorted key order.
|`relationships` |For each receipt, its asset ids and linked journal ids, sorted by id.
|===

`archiveManifestToJson` and `archiveManifestFromJson` convert to and from JSON. Encryption of the archive itself belongs to the store.

=== Store archive layout

The store's `exportBackup` writes the entries in this order: `data/workspace.json`, `data/accounts.json`, `data/categories.json`, `data/journals.json`, `data/entities.json`, `data/assets.json`, `pending_commands.json`, `files/<assetId>` for each receipt file present on the device, `csv/transactions.csv` and `csv/accounts.csv` (optional), and `manifest.json` last. Its manifest records the format, format and schema versions, the database schema version, the accepted cursor, pending command count, record counts, a SHA-256 and size for every file, relationships and the number of unbalanced journals. Assets whose bytes were not on the device (evicted or never downloaded) are not in the archive and are reported as unavailable in the export summary.

NOTE: The store's `manifest.json` (`packages/finance_store/lib/src/backup`) and the core `ArchiveManifest` model are two related shapes of the same idea. The store manifest keys files in a map and groups counts under `counts`, while the core model lists files in an array with roles. Restore verification exists in both layers and checks the same properties.

=== Encrypted container

The whole archive is wrapped in the `FSBACKUP` container: AES-256-GCM chunks with a key derived by Argon2id from the recovery secret. The container layout, key derivation and tamper detection are described in xref:architecture:local-store.adoc[].

== Restore verification

Restore is verified before anything is applied, into an isolated workspace, and the person sees a preview. `verifyArchive` (acceptance scenario A16: restore a full encrypted export on a fresh device) checks in order:

. Format and schema compatibility (`FORMAT_UNSUPPORTED`, `SCHEMA_UNSUPPORTED`).
. Every manifest file is present with the recorded size and SHA-256 (`MISSING_FILE`, `SIZE_MISMATCH`, `HASH_MISMATCH`). Extra files are a warning, `UNEXPECTED_FILE`, and are ignored.
. Every journal balances (`UNBALANCED_JOURNAL`) and is in the manifest currency (`CURRENCY_MISMATCH`).
. Record counts equal the manifest (`COUNT_MISMATCH`).
. Every receipt relationship points at a verified stored asset (`MISSING_ASSET`) and a restored journal (`DANGLING_RELATIONSHIP`).

The `RestorePreview` carries the manifest, the issues, expected and actual counts per entity type, the number of verified files and the number of pending local changes. `canRestore` is true only when no issue has error severity. Pending local changes are shown separately and are never replayed into a live workspace.

The store's `stageRestore` produces a `RestorePreview` (a separate class from the core one of the same name) with expected and restored counts, checksum failures, missing and unavailable assets, unbalanced journals, pending commands and the accepted cursor. The restored workspace is staged beside the current one with a new workspace id and device id, starts local only, and nothing touches the target until it is activated. `canActivate` requires a compatible schema, no checksum failures, no missing assets, no unbalanced journals and matching counts.

== Delivering files [[delivering-files]]

Backups, the CSV export, the receipts export and the financial year pack all leave the app through a `FileExporter` (`apps/finance_app/lib/platform`). iOS and Android do not offer the save and folder dialogs that `file_selector` provides on desktop ("Choose a save location" is unsupported on both, and "Choose a directory" on iOS), so on a phone these exports previously did not work. There are two implementations.

* `DesktopFileExporter` uses a save dialog for a file and a folder dialog for a folder. If the chosen folder already exists, the export is written to a new one named with `-2` and so on, and nothing is written over.
* `ShareFileExporter` uses the share sheet. A folder is shared as one zip file. The temporary copy holds unencrypted receipts, so it is deleted once the share finishes. The `share_plus` plugin keeps its own copy in the app's cache. It is not removed as soon as the sheet closes because the receiving app may not have read it yet. The app deletes it ten minutes after a share, at once if the person backed out or sharing failed, and on the next start if the app was closed before then. A new share cancels the pending deletion, since the plugin replaces the copy itself. If the app is killed during the share, the working folder is deleted at the next start. Only start-up removes working folders; a finished share removes only the plugin's copy, so that one export can never delete the folder of another still in progress.

A backup is recorded as made (and the reminder cleared) only once the person has kept it, and a failure is shown rather than ignored.

Restoring a backup on iOS did not work before, because the file picker refuses a filter that has no type identifier. On phones the filter now offers all files, and the restore checks what was chosen. This has been run on the iOS simulator and on an Android emulator release build: a backup was made and restored on each, including a backup made on iOS and restored on Android.

== In the application

* *Backup reminders (DATA 02).* Data kept only on the device can be recovered only from a backup the user made, so for a local-only workspace the Overview page shows a reminder with a "Back up" action. It appears when the data has never been backed up and at least 10 changes were made, when the last backup is 30 or more days old and there are newer changes, or when 200 or more changes have been made since the last backup. Preferences and entry drafts are not counted. A synced workspace shows no reminder. `AppState.recordBackup` records the time and change count that the reminder compares against, and the backup action in settings calls it after `exportBackup`, so making a backup clears the reminder until new data changes or 30 days pass.
* *Storage report and freeing space (NFR 10).* Settings shows how much space the device uses: receipts, readable copies, previews and the database, and, for a workspace that syncs, how much of that is not yet backed up to the server and is never removed. A device-only workspace omits that amount. When local copies of receipts that are confirmed on the server exist, "Free" removes the least recently used ones. Previews and unsynced files are never removed.
* *Financial year pack.* Settings, "Financial year pack" asks for a July to June year, listed newest first from the year of the earliest entry to the current year, and produces a folder such as `finance-FY2025-26`:
** `transactions.csv`: that year's entries, in the same format as the transaction export.
** `summary.csv`: the columns `Section`, `Item` and `Amount`, holding income, expenses and net totals, spending by category, spending by tag, and what was owed to the person at the end of the year. The figures come from the same reports the app shows, and names are sanitised against spreadsheet formulas.
** `receipts/`: the original files and a `manifest.json`, in the same format as the receipts export.
** `README.txt`.
+
A receipt belongs to the year of the entries it is attached to. A receipt attached to nothing goes by its own date, and otherwise by when it was captured. Files held only on the server are listed in the manifest but not copied, and the app says how many. The pack is a record of what was entered. It is not tax advice and does not work out what can be claimed, because tax return preparation is outside the product's scope.
* *Receipt export (EXP 01).* "Export receipts" writes the original files and a `manifest.json`; see xref:platform:receipt-capture.adoc[]. It is not a backup and is not restorable.
